**Class A — preserved-libs registry serialization / empty write.** Real's
`PreservedLibsRegistry.store()` is `json.dumps(..., indent="\t", sort_keys=True)` and
only rewrites on a change: with no preserved-lib activity the packaged empty file stays
**0 bytes** (C1/C3/C4), and an empty registry real *does* write is exactly `{}` (2
bytes, no trailing newline; C2). Portuale's `ebuild_merge::write_plib_registry` is
called from `register_preserved_libs` / `unregister_preserved_libs` /
`prune_unused_preserved_libs` unconditionally
(`rust/portuale/src/ebuild_merge.rs:1203`, `:1414`, `:1594`) and emits `"{\n"` … `"}\n"`
(`:1116`), so an empty registry is `{\n}\n` (4 bytes) and a non-empty one gains a
trailing newline real omits.

**Class A also covers the C2 registry *content* — the exact shape the C2 cell exists to
check — which the first pass missed.** The candidate run's
`C2/candidate/portuale.logs/preserved_libs_registry-after.txt` (4-byte `{\n}\n`
included) records the owner cpv `l32/sonamelib-1.0` and the path order
`[…/libl32soname.so.1, …/libl32soname.so.1.0.0]`; the reference side
`C2/candidate/portage.logs/preserved_libs_registry-after.txt` records
`l32/sonamelib-2.0` with the **reversed** order `[…/libl32soname.so.1.0.0, …so.1]` —
byte-for-byte the S0 oracle's `[I]`-blessed shape ("Comparator keys: … the owner cpv
`l32/sonamelib-2.0`; the path list order (`.1.0.0` then `.1`)", `## Group 2` below).
So the divergence is not just size/format: the registry names the *wrong owner* (the
pre-bump cpv, which no longer owns the files) and the *wrong path order*, both named
oracle comparator keys. This is the same registry and the same
`write_plib_registry`/`register_preserved_libs` call family as the size/format half, so
it is one mechanism family, not two classes; the fix direction in #167 must therefore
also assign ownership to the **new** (post-bump) cpv and order the preserved path list
`…so.1.0.0` before `…so.1`, or the #167 fix would leave the cell's central shape
unfixed.

**Class B — `--resume` after SIGKILL has no resume list.** The C4 kill left `mtimedb`
with no `resume` key (`mtimedb-resume-key.txt`: `resume key present: False`). Both
`emerge --resume --pretend` and `emerge --resume` then exit 1 with
`emerge: could not find a valid resume list` (`rust/portuale/src/pretend.rs:4928`), so
`l32/slow-c` is never merged (vdb 2 vs real's 3). Real records `mtimedb["resume"]`
(`favorites` reversed, the full `mergelist`, `myopts`) at merge start and replays all
three with rc 0. Portuale only writes on a *clean failure* (`pretend.rs:5085`, `:13108`,
`:13146`) and rotates an existing list to backup before a fresh merge (`:13002`); nothing
is persisted before the first merge executes, so a `kill -9` loses the plan.
`read_resume_list` / `run_resume` already replay a saved list — the gap is the up-front
save.

## Real-vs-design disagreements / capture limitations

1. **S1/S2 split conflict** — resolved above (S1 = groups 1–4, S2 =
   group 5). The plan's parenthetical "(no fault injection)" does not match
   the five-group list, because group 4 is itself a SIGKILL fault.
2. **No product code, but two Portage 3.0.82.2 behaviours matter to the
   design:**
   - the vdb holds **no `_cfg`/`_cfgpro` marker** and **no `preserved`
     file**; the only artifacts are the on-disk `._cfg0000_*` /
     `/var/lib/portage/preserved_libs_registry`. Any portuale design that
     expects a vdb marker is a real-vs-design disagreement.
   - `--resume` re-merges **from the start of the merge list** and consumes
     the `resume` key only on success; it does not skip the interrupted
     package. Portuale must match the mtimedb `favorites` (reversed) /
     `mergelist` shape and the `*** Resuming merge...` prefix.
3. **F2 corrupt cell is not clean** — the test root already had
   `faultpkg-1.0`, so "no partial vdb entry" is unproven; only the digest
   failure shape and rc `1` are trustworthy. Re-capture on a clean root.
4. **F3b fallback is not clean** — source fallback was selected but the run
   died with `OSError: [Errno 28]` and rc `143`; re-capture on a root with
   free space before using it as an S2 oracle. F3a (fail, rc 1) is clean.
5. **disk-full rc is 143, not 1** (both F1a and F1b). The ENOSPC appears
   first as a Portage-internal `PipeLogger` flush crash on Python 3.14. The
   S2 comparator should key on the message shape
   (`OSError: [Errno 28] No space left on device`, `dd: error writing
   ... No space left on device`, `ERROR: … failed (install phase)`) and on
   the VDB/workdir delta, not on exit code alone.
6. **Pretend-vs-actual shape gap:** `-p -C` omits the
   `Waiting 5 seconds`/`Unmerging in: 5 4 3 2 1`/`Unmerging (1 of 1)` block
   that the actual `-C` prints; `--depclean` actual replaces
   `Number to remove` with `Number removed`. A comparator must key on the
   right set per invocation.
7. **Pre-flight profile missing:** `df -h /home`, `df -i /tmp`, and
   `nice -n 19` are required by the brief but are not present in the run
   dir. S1/S2 must record them per cell (and keep the disk-full cell on a
   dedicated tmpfs, as here).
8. **The `--depclean` actual can be safety-blocked** — the capture only ran
   it because `depclean-pretend-after.outside-count` was `0`. The bed must
   reproduce that guard: never let `--depclean` target non-fixture
   packages.
9. **Soname registry middle field (`464`)** is opaque Portage state; the
   comparator should key on `cp:slot`, owner cpv, and the path list, and
   ignore that integer.
