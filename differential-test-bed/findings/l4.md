| path | real Portage merge | `mrg` remote merge |
|---|---|---|
| `/usr/bin/pt-setuid` | **4711** | **711** |

### Disagreements between real behaviour / design and what shipped

Recorded, **not resolved and not fixed** (S0 constraint).

1. **Status channel (§6/§11 vs code).** Design: each stage emits
   `portuale-remote: <stage> <rc>` on a dedicated fd, "stderr stays the
   human log". Reality: no `portuale-remote:` token exists anywhere in
   `rust/portuale/src` (grep `portuale-remote:` → only the plan doc); the
   machine tokens (`STATUS=`, `MERGE_*=`, `PHASE_*=`, `UNPACK=`) go to
   **stdout**, interleaved with the `>>>` human lines;
   `mrg-local.stderr.txt` / `mrg-ssh.stderr.txt` are essentially empty.
   S1's comparator must key off the actual tokens, not the §6 spelling.
2. **Option surface (§10 vs `mrg.rs` OPTIONS).** `--remote-keep-workdir`
   is in the §10 table but clap rejects it ("unexpected argument");
   `--remote-jobs` is likewise absent (the table calls it a reserved
   knob). The other 18 `--remote-*` options are present. (This is why the
   run's workdir could not be retained for forensics; the mode-loss root
   cause was localized by extracting the gpkg directly instead.)
3. **Stage count (§11 "one `bash -s` per stage-group").** Reality is one
   ssh invocation per sub-step: 5 (hookless) or 7 (with hooks), per unit.
   Multiplexing keeps it one TCP/auth (§4), but "stage-group" is not
   literal.
4. **Format in tests vs target (§1).** The only shipped full-remote-merge
   tests drive `--remote-binpkg` with **xpak** `.tbz2` fixtures; §1
   declares xpak out of scope and gpkg the target. This capture proves the
   gpkg path works end to end (`mrg-gpkg*.stdout.txt`), so S1 should use
   gpkg. Recorded so the S1 runner does not inherit the tbz2 habit.
5. **Modes (product bug).** Real Portage preserves setuid/setgid/sticky;
   `mrg` remote does not (see "Must preserve" 4). §6's receive stage's
   `tar -xf` without `-p` is the localized cause.
6. **Owner semantics.** Real Portage merged as root (`root:root`, parents
   `bin:bin`); the remote client is the login user who owns ROOT
   (`1000:100`). Before S1 grades any owner row it must fix the control
   pair to a single user on both sides, else every row is an artefact.

### Mode boundary (re-derived — capture/analysis, no fix)

The special-bit loss is **client-uid dependent**, and there are **two
product sites**, not one:

- **Root client (uid 0; S1's topology, FAR = the container `/`):** the
  receive-stage `tar -xf "$BUNDLE"` **preserves** all bits (GNU tar is
  `-p` by default for root). The loss is the merge copy driver's order:
  `chmod --reference "$src" "$tmp"` then `chown --reference "$src" "$tmp"`
  in `MERGE_FLOW`'s obj branch (`remote.rs`). Linux `chown(2)` clears
  `S_ISUID`/`S_ISGID` on a regular file **even when the owner does not
  change**, and leaves the sticky bit alone: `4711/2755/1750` →
  **`0711`/`0755`/`1750`**. (`pt-sticky` surviving is the tell that the
  root-case loss is not the tar.)
- **Non-root client (uid > 0; S0's host capture):** the receive
  `tar -xf` **without `-p`** strips all three special bits at extraction
  (`0711`/`0755`/`0750`); the copy stage (which skips `chown` for
  non-root) never sees them. `tar -xp` keeps `4711/2755/1750`, and a
  non-root copy of already-special bits preserves them, so the receive
  stage is the non-root site.

S0's single-site localisation to the receive stage was therefore an
artefact of its `uid 1000` host client: under root `tar -xf` is
**innocent**. Fixing only the tar leaves root clients broken; fixing
only the chown order leaves non-root clients broken — both sites belong
to **#169**.
