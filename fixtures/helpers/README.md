# Helper oracles (plan #326 S2, decisions D3/D4)

Expected values for the native ports of the small Portage helpers,
generated by RUNNING the real helpers against `3rdparty/portage`
(never by reasoning about them). The Rust tests in portuale read these
through its `fixtures` symlink (`portuale/fixtures -> ../pmtest/fixtures`),
so they run without a Portage checkout.

## Layout

- `generate.sh` -- regenerates everything below (bash; see its header).
  Run it as `fixtures/helpers/generate.sh`; the checkout path defaults to
  the sibling `../portuale/3rdparty/portage` and can be overridden with
  `$PORTAGE_CHECKOUT`. It runs every chmod-lite case twice (as the invoking
  user and as root via passwordless sudo) on freshly built trees under
  `/var/tmp/pmtest`, which it removes afterwards.
- `chmod-lite/<case>/` -- one oracle per input tree:
  `in.manifest` (checked in, the input's source of truth),
  `out.manifest` / `out.root.manifest` (user / root results),
  `stderr.txt` / `stderr.root.txt`, `rc.txt` / `rc.root.txt`, and `README`
  (what the case isolates, its regression signature, provenance).
- `filter-env/<case>/` -- one oracle per (pattern, stdin) pair for
  `bin/filter-bash-environment.py`: `args` (checked in, argv[1] exactly
  as bytes, no trailing newline added), `in` or `in.bz2` (checked in,
  stdin bytes raw or bzip2-compressed when the raw input exceeds
  64 KiB), `out` or `out.bz2` (regenerated, matching the input form) /
  `stderr.txt` / `rc.txt` (regenerated), and `README` (what the case
  isolates, its regression signature, provenance). A reader must accept
  either form: if `in.bz2` is present the stdin bytes are its bzip2
  decompression (likewise `out.bz2` for stdout). Regenerated by
  `generate-filter-env.sh` (called from `generate.sh`).
- `gpkg/` -- `gpkg-helper.py compress` oracles (S4), compared field by
  field through `out.fields`; layout and format in `gpkg/README.md`;
  regenerated by `generate-gpkg.sh`. `gpg-keyring/` is the signing key it
  uses.
- `xpak/<case>/` -- `xpak-helper.py recompose` oracles (S5), compared byte
  for byte; layout in the `generate-xpak.sh` header.

## Manifest format

One line per entry, sorted by path, relative to the tree root:

```
<type> <octal mode, 4 digits> <path>[ -> <symlink target>]
```

`type` is `d`, `f` or `l`; for `l` the mode is always `----` and a
` -> <target>` suffix carries the raw `readlink` bytes. Paths are
`/`-separated; every byte outside `[A-Za-z0-9._/+-]` is percent-encoded
as `%XX` (uppercase hex), so manifests are pure ASCII and git-safe --
non-UTF-8 names (case `non-utf8`) never appear raw. Only type, mode, path
and target are recorded: file contents are empty (out of scope) and the
tree root itself (the WORKDIR analog, which real `find` skips) is not
listed. `generate.sh` validates this format strictly when building trees.

## Rebuilding trees from a manifest

Decode `%XX` to raw bytes and use byte paths throughout (argv/str paths
mangle non-UTF-8 names). Set modes deepest-first after creating children,
so `0000` dirs can still be populated. One advisory from generating these
on this host: a filesystem may reject non-UTF-8 names outright (this
host's zfs dataset answers `EILSEQ`); `generate.sh` probes for that and
stages the `non-utf8` tree on a tmpfs bind mount when needed. Test
harnesses must likewise materialize trees where arbitrary bytes are
accepted (`/tmp` works here; the repo checkout does not).

## Regenerating

```
fixtures/helpers/generate.sh
```

A second run on the same host is byte-identical except the `date:` line
(UTC day granularity) in the `chmod-lite/*/README` and
`filter-env/*/README` files, which is the only intentionally varying
field.

## filter-env case kinds

`captured-<ebuild>-<phase>` holds one real invocation verbatim: `args`
is the pattern argv[1] as captured, `in` the captured stdin. The
patterns were captured, not reconstructed: real Portage 3.0.82.2 ran
two `porttest` probes (`phases`, `helper-unpack`) phase by phase in a
`localhost/test-portuale:latest` container with
`bin/filter-bash-environment.py` replaced by a logging wrapper (argv[1]
+ stdin recorded per call, then the real script re-executed with
identical argv + stdin). Running `ebuild <path> <phase>` for each phase
in lifecycle order yields one end-of-phase save per phase
(`___save_and_filter_ebuild_env --filter-features`), plus the
build-info save inside `__dyn_install`
(`--exclude-init-phases --filter-path --filter-sandbox
--allow-extra-vars`, the `install-buildinfo` cases -- the same option
set as the merge-time `PORTAGE_UPDATE_ENV` regen, which is not reachable
through the `ebuild` command). The unpack command re-ran pretend/setup
first (its clean wiped their stamps); those re-saves differed from the
dedicated captures only in BASHPID/PPID and were deduped. The
preprocess option set (`--filter-features --filter-locale --filter-path
--filter-sandbox`) never occurred (no `environment.raw` on source
builds). All runs had `EMERGE_FROM=ebuild`, which takes the same pattern
branch as a source merge; the `EMERGE_FROM=binary` branch was not
reached. The cases are one per (`ebuild`, phase): `pretend`, `setup`,
`unpack`, `prepare`, `configure`, `compile`, `test` (observed during
the `install` run, which chains test first), `install`,
`install-buildinfo`, `preinst`, `postinst`.

`fixture-env-<n>` is every `environment.bz2` under pmtest `fixtures/`
(there are two, both tiny) decompressed, with the captured
install-phase pattern as `args`.

`pkgcache-<cat>-<pf>-<build>` is every distinct `environment.bz2`
from the L1 pkgcache sample
(`differential-test-bed/logs/_l1-pkgcache`, 64 real-Portage-built
binpkgs, all gpkg): each binpkg's `metadata/environment.bz2`
decompressed, with the captured end-of-phase pattern P1 (2378 bytes,
byte-identical to `captured-phases-install/args`) as `args`. The 64
binpkgs collapse to 28 unique inputs (deduplicated by SHA-256 of the
decompressed bytes; near-duplicates differing only in `L1_JOBS` are
kept as separate cases). Inputs whose raw size exceeds 64 KiB are
stored compressed as `in.bz2`/`out.bz2` (`bzip2 -9`); smaller ones stay
raw as `in`/`out`. The generator re-extracts from the pkgcache when it
exists and otherwise keeps the checked-in `in`/`in.bz2`, recomputing
only outputs.

`edge-*` are hand-written byte inputs against the captured
install-phase pattern (unless the case needs another pattern, said in
its `README`): here-doc inside a function, byte 0x01, a multi-line
value ending in `\"`, `declare -ar`, `declare -- x`, the `declare -r`
rewrite, UTF-8 and invalid-UTF-8 names, a last line without trailing
newline, empty input, and regex metacharacters from the real caller
vocabulary. `error-bad-pattern` pins real's non-zero exit (rc 1 with a
`re.error` traceback): no real caller produces it, and the argc-based
usage error (rc 2) cannot occur through this layout, which always
passes exactly one pattern argument.
