### FIXED — `l3-subslot-self-collision`: `-e`/reinstall of a sub-slotted
package aborted on its own files

First smoke run (`TEST/logs/l3-20260914T011319Z`): portuale's build
reached `sys-libs/ncurses-6.5_p20251220` (`SLOT="0/6"`) and aborted
"Package 'sys-libs/ncurses-6.5_p20251220' NOT merged due to file
collisions" with every ncurses file listed.

- Expected (real, same image): `emerge -e` reinstalls ncurses over
  itself; own files are `others_in_slot`, never collisions.
- Root cause: `ebuild_merge::merge_after_install` passed
  `parse_slot(ebuild)`'s **full** `"0/6"` to `find_collisions`/
  `installed_instance_pf`/`blocked_installed_packages`, but those
  compare against the vdb `SLOT` file's **main** slot (`read_installed_
  slot` strips the `/sub`). `own_versions` was empty, so every file
  looked foreign and `FEATURES=protect-owned` (real's default) aborted.
  `merge_binpkg` already used `main_slot`; the source path did not.
- Fix: `ebuild_merge.rs` computes `main_slot` for the ownership checks,
  keeps the full slot for the vdb `SLOT` write. Regression test
  `re_merging_a_sub_slotted_package_does_not_collide_with_its_own_files`
  + fixture `fixtures/repo/dev-libs/subslotfilepkg` (`SLOT="0/1"` with
  a real file).

### FIXED — `l3-config-multi-assignment-stacks`: a second incremental
assignment in one config file replaced for real, stacked for portuale

The candidate VDB env carried `FEATURES` tokens (`noinfo
observability split-elog split-log`) that real's did not:

```
podman run ... IMAGE -c 'printf "\nFEATURES=\"-buildpkg sandbox splitdebug\"\n" >> /etc/portage/make.conf; emerge --info | grep ^FEATURES'
# real: the image's own FEATURES line is gone -- the last assignment in
# the file is the file's only layer (bash sourcing semantics).
```

- Expected: `make.conf` is sourced; for an incremental variable the
  file's layer is its **final** assignment, not every assignment
  stacked.
- Root cause: `portage_profile`'s `note_incremental` pushes one source
  per assignment, so the image's `FEATURES` line and the L3 block's
  stacked.
- Fix: `IncrementalSnapshot::take`/`restore` collapse each processed
  file's tracked incrementals to the final assignment; applied to
  `make.globals`, each profile `make.defaults`, `make.conf` (top-level,
  sourced sub-files included) and `env.d`'s `profile.env`. Test
  `a_files_incremental_layer_is_its_final_assignment`. The harness's
  determinism block now **replaces** the image's `FEATURES` line
  instead of appending a second one (same file semantics).

### #44 — ncurses OWNER `1:1` vs `0:0`: the hypothesis is H2, with the exact rule

```
real   install.post : D 0:0 curses.h      ROOT 1:1  (pre-merge, stage3)
real   postinst.post:                     ROOT 1:1  /usr/include/curses.h
                                          ROOT 1:1  /usr/share/terminfo/x/xterm
                                          ROOT 0:0  /usr/include/ncurses.h
port.  install.post : D 0:0 curses.h      ROOT 1:1
port.  postinst.post:                     ROOT 0:0  (all three paths)
```

- **H1 is false**: real's `${D}` is `0:0` for all three paths; the install
  phase does not produce `1:1` (`ownership.txt`, `install.pre/post`).
- **H3 is false**: both containers are the same image, the stat is plain
  `stat -c`, and real's own live root is `1:1` before the merge and for
  two of the three paths after.
- **H2 confirmed, mechanism identified**: real's merge keeps the
  destination's ownership only where it does not move the file at all.
  `dblink.mergeme` calls `movefile` only when
  `dblink._needs_move(mysrc, mydest, mymode, mydmode)`
  (`3rdparty/portage/lib/portage/dbapi/vartree.py:5916`, definition
  `:6363`) is true; `_needs_move` returns **False** for an existing
  regular file with the same mode, equal xattrs and
  `filecmp.cmp(shallow=False)`-equal content, so the destination's
  inode/ownership/mtime survive byte-identical rebuilds (bug #722270).
  A symlink never reaches `_needs_move` (docstring: "Should only be used
  for regular files") and goes through `movefile`'s symlink branch, which
  recreates it with the source's `0:0`.
- This is exactly the shape here: `/usr/include/curses.h` and
  `/usr/share/terminfo/x/xterm` are **identical regular files** (same
  version, byte-identical rebuild), so real skips the copy and they stay
  `1:1`; `/usr/include/ncurses.h` is a **symlink → curses.h**, so real
  replaces it and it becomes `0:0`; portuale copies everything, hence
  `0:0` everywhere. P1's fix is therefore "skip the copy for an
  identical-mode, identical-content existing regular file", mirroring
  `_needs_move`/`mergeme` — not a blanket ownership preserve.

### Symptom 1 — `A` (distfiles): **no longer reproduces, no P2b work**

Live `A` is the identical single flattened list on both sides at every
phase (`vars.txt`, `A^1` on real and portuale from `setup.pre` through
`install.post`), and the fresh vdb env has it once on both sides (`diff`

(`l3-20260914T021049Z`, still quoted in the #45 filing) is closed by the
intervening config/env work between that run and P0 — no phase boundary
or save path in the current tree shows it.

### Symptom 2 — `RESTRICT="test test"`: env assembly, first phase, one root cause

Portuale's live `RESTRICT` is `"test test"` already at the **first** phase
(`pretend.pre`; identically `setup.pre`), real's is `"test"` at
`setup.pre` — so this is not cross-phase accumulation, it is the phase
env portuale hands to the first bash process.

- Root cause: `ebuild_phases.rs::restrict_and_properties` computes
  `PORTAGE_RESTRICT` as `flat_field_on(metadata["RESTRICT"], use_set)`.
  ncurses' `RESTRICT="!test? ( test ) test"` use-reduces (with `test`
  disabled) to two `test` tokens, and `flat_field_on` keeps both.
  `bin/ebuild.sh:721-724` then overwrites `RESTRICT=${PORTAGE_RESTRICT}`
  for every non-`depend` phase, which is why the live var (and the saved
  env) carries the duplicate.
- Real counterpart: `config.py::_flatten` (`3rdparty/portage/lib/portage/
  package/ebuild/config.py:1681-1688`) —
  `" ".join(sorted(set(use_reduce(settings.get(var, ""), uselist=use,
  flat=True))))` — a **set**, deduped *and* sorted. (`PROPERTIES` goes
  through the same helper, so the fix belongs in the one shared
  function.)

### Symptom 3 — `declare -- f` / `declare -- x=""` in the vdb env: post-merge regeneration missing

The live envs are symmetric: `x` shows up on **both** sides
(`declare -- x` at `configure.pre`, `declare -- x="pre_pkg_preinst"` at
`preinst.pre` — real's own `__ebuild_phase_with_hooks` loop local), `f`
on neither; and the P0 `${T}/environment` snapshots have neither on
either side. The two vdb envs nevertheless differ (`f` and `x=""` only
under portuale), so the divergence is in *which save writes the vdb
env*:

- Real `dblink.treewalk` sets `PORTAGE_UPDATE_ENV=<dbpkgdir>/
  environment.bz2` before the **postinst** phase of *every* merge
  (`vartree.py:5333-5341`), so `bin/phase-functions.sh:1072-1082`
  rewrites the vdb env from the hook's live environment through
  `__save_ebuild_env --exclude-init-phases | __filter_readonly_variables
  --filter-path --filter-sandbox --allow-extra-vars | bzip2 -9` — the
  path whose filter drops those globals.
- Portuale's **source** merge runs the same postinst hook *without*
  `PORTAGE_UPDATE_ENV` (`vars.txt`: empty at portuale's `preinst.*`/
  `postinst.*`; real shows the dbpkg path), so the vdb entry keeps the
  install-time `build-info/environment.bz2` (`__dyn_install`'s tail save)
  with the stray globals in it. Root-cause site:
  `ebuild_merge.rs::merge_after_install`'s postinst-hook invocation (the
  binary path already passes `update_env`; the source path does not).

## P1 — #44 fixed: identical files are not moved (2026-09-14, wave 2 of the Tier5/2 slicing)

`ebuild_merge.rs` now mirrors real `dblink._needs_move`
(`vartree.py:6363`, bug #722270) at the regular-file merge site: before
`std::fs::copy` of a destination that already exists, `needs_move(src,
dest)` compares the two lstat modes and the bytes (chunked
`files_equal`); an identical destination is left completely in place
(only its mtime is refreshed, real's `os.utime`), so its inode,
ownership and xattrs survive a byte-identical rebuild. A diverted
`._cfgNNNN_` write always moves (`write_dest != dest`, mirroring real
clearing `mydmode` on a protected write). Documented narrowing: real's
`FEATURES=xattr` `_cmpxattr` comparison is treated as equal (portuale's
merge copies no xattrs).

Regression test:
`tests/test_portuale.py::test_merge_skips_an_identical_file_preserving_ownership`
(runs the merge as root via passwordless `sudo`; pre-creates the
identical `1:1` destination, asserts ownership/inode survive the second
merge, then a content bump flips it back to the source's `0:0`).
Verified failing on the pre-fix merge code and passing with the fix.

Evidence runs:

- L3 smoke candidate pair, `TEST/logs/l3-20260914T132606Z`

### #47 — the `BUILD_TIME` producer gap, fixed

Real `_post_src_install_write_metadata` (`doebuild.py:2727-2732`)
writes `int(time.time())` into `build-info/BUILD_TIME` *before* any
other metadata key; `dblink.treewalk` copies it into the vdb
(`vartree.py:4911-4913`) and `_consolidate_to_metadata_file` folds it
into the `metadata` body (`vartree.py:232`). Portuale's
`write_post_install_metadata` (`ebuild_phases.rs`) had the
IUSE/IUSE_EFFECTIVE/SIZE halves but not this line, so every
source-merged vdb entry differed from real's by the standalone file
*and* the consolidated field (12 VDB rows per smoke run). Fixed at the
top of that function, before its repo-metadata early returns (real's
write is unconditional), pinned by the
`install_writes_the_real_build_time_file` unit test. The candidate's 12
rows are gone.

```sh
    QA_DESKTOP_FILE QA_PREBUILT PROVIDES_EXCLUDE REQUIRES_EXCLUDE \

```

not) is `dev-build/ninja`'s own ebuild: `src_compile()` starts with
`unset CFLAGS` (`ninja-1.13.2-r1.ebuild:84`). Real keeps that unset
across phases via `config.environ()`'s `filter_calling_env`
(`lib/portage/package/ebuild/config.py:3274-3305`, real bug #189417):

```python
        filter_calling_env = False
        if (
            self.mycpv is not None
            and not (emerge_from == "ebuild" and phase == "setup")
            and phase not in ("clean", "cleanrm", "depend", "fetch")

            if temp_dir is not None and os.path.exists(
                os.path.join(temp_dir, "environment")
            ):
                filter_calling_env = True
        ...
            if (filter_calling_env and x not in environ_whitelist
                    and not self._environ_whitelist_re.match(x)):

                # environment unless it is explicitly whitelisted.
                # This ensures that variables unset by the ebuild
                # remain unset (bug #189417).

```

Once `${T}/environment` exists, every later phase spawns with only the
`special_env_vars.environ_whitelist` config/calling-env keys (`CFLAGS`
is not one) and the saved environment supplies the rest — so
`src_install` sees no `CFLAGS`, `__dyn_install` writes no
`build-info/CFLAGS`, and the vdb row never appears. portuale's phase
env re-injected its config `build_env` (`CFLAGS` and friends) into every
phase, so the `unset` never reached `src_install`.

Hermetic fixture (pmtest `fixtures/repo/dev-libs/unsetcflagspkg/`, md5
cache alongside): `src_compile` is just `unset CFLAGS`, `src_install`
records `${CFLAGS-<unset>}` / `${CXXFLAGS-<unset>}` and merges the
record so a test can assert the install view and the vdb row set.
Before the S1 fix the recorded install view is
`CFLAGS=-O2 -pipe\nCXXFLAGS=-O2 -pipe\n` and the vdb carries `CFLAGS`;
after it, `CFLAGS=<unset>\nCXXFLAGS=-O2 -pipe\n` and the vdb has no
`CFLAGS` row while `CXXFLAGS` stays. The S1 Rust regression test
(`source_merge_omits_a_vdb_aux_file_the_ebuild_unset_in_an_earlier_phase`)
pins exactly that.
